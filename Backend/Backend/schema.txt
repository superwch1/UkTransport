Part 1 — The rules, as written
1.1 Override precedence (§3.18.5, Table 3 - 17)

1 VehicleJourneyInterchange
2 VehicleJourney
3 JourneyPatternInterchange
4 JourneyPattern
5 Service
Rule 1 (§3.18.5): "Elements specified for a given profile property at a lower level of discourse completely replace the equivalent element at a higher level."

I need to correct what I told you last turn. The base spec overrides per property, not per whole element. Table 14-5 confirms it: the 33 date rules fall through individually, so a VehicleJourney that specifies RegularDayType but omits BankHolidayOperation still inherits the Service's BankHolidayOperation (rules Sx3/Sx4 are reached).

But PTI §5.3.3.1 overrides this for BODS: a VehicleJourney must have "either (a) no OperatingProfile … or (b) a complete set of OperatingProfile elements which completely replace the default pattern", and §9.1: "complete sets of information shall be overridden, and the systems shall not rely on inheriting only parts of data elements." So your ?? chain is correct for BODS-conformant files and diverges only on legacy/non-conformant ones.

1.2 Day resolution (§14.4, Table 14 - 5)
Not a flag model — an ordered 33-rule include/exclude walk per date. Highest precedence first, grouped VehicleJourney → JourneyPattern → Service, and within each level:

Order Rule	Effect
1	Service/OperatingPeriod	                        bounds everything
2	SpecialDaysOperation/DaysOfNonOperation	        exclude
3	SpecialDaysOperation/DaysOfOperation	        include
4	BankHolidayOperation/DaysOfNonOperation	        exclude
5	BankHolidayOperation/DaysOfOperation	        include
6	ServicedOrganisationDayType/DaysOfNonOperation	exclude
7	ServicedOrganisationDayType/DaysOfOperation	    include
8	ServicedOrganisation ancestors (ParentRef)	    exclude/include
9	PeriodicDayType/WeekOfMonth	                    exclude
10	RegularDayType/Days	                            include
Plus the governing principles (§3.18.5): exceptional overrides regular; exclusion constrains, inclusion adds; non - operation always beats operation; PeriodicDayType and ServicedOrganisationDayType are logically ANDed with RegularDayType (§6.11.1).

1.3 Defaults
Situation	Spec default
No OperatingProfile at any level	            Monday–Friday, every day of year (§6.11, Table 3 - 7)
OperatingProfile present, no RegularDayType	    MondayToSunday (§6.11.1, §3.18.10.2a)

1.4 Timing (§3.7.2)

Arrival(n)   = Departure(n-1) + RunTime(link n-1→n)
Departure(n) = Arrival(n) + WaitTime
Two things the schema guide gets wrong and PTI §8.4.3 corrects: "In TXC v2.4, this behaviour fundamentally changed. The schema guidance, unfortunately, did not reflect this… From version 2.4 onwards, the wait time was to be the total wait time and was to be stated identically on both the To element of the incoming link and the From element of the next, outgoing link." So in 2.4+ you take it once; the guide's "add both ends" formula is the pre-2.4 rule.

VehicleJourneyTimingLink overrides JourneyPatternTimingLink for RunTime and WaitTime (§6.8.4.1, Table 3 - 7). PTI §8.1 explicitly blesses two encoding styles:

…a JourneyPatternTimingLink set for every different combination of link duration, wait time and stop activities…
…a single JourneyPattern…with each link duration and wait time set to zero minutes. This method uses the facilities in the vehicle journey to override the default zero-minute durations for each of the links.
1.5 Journey linking (§6.8.1)
VehicleJourney references its pattern by one of:

JourneyPatternRef — normal case, or
VehicleJourneyRef — "Reuse the VehicleJourneyTimingLink elements of the referenced VehicleJourney, and follow its JourneyPattern"
Also: Activity ∈ {pickUp, setDown, pickUpAndSetDown, pass} — pass means the bus does not stop. DepartureDayShift ∈ {−1, 0, +1} shifts which operating day a journey belongs to. DeadRun/ShortWorking lets a journey start or end partway along its pattern. Frequency makes one VehicleJourney stand for many departures.

1.6 Vocabulary (from the XSD, not memory)
DaysOfWeek: Monday…Friday, Saturday, Sunday, MondayToFriday, MondayToSaturday, MondayToSunday, Weekend, NotMonday, NotTuesday, NotWednesday, NotThursday, NotFriday, NotSaturday. There is no NotSunday.

Bank holidays — 22 individual values plus 6 umbrella groups (AllBankHolidays, Christmas, AllHolidaysExceptChristmas, HolidayMondays, DisplacementHolidays, EarlyRunOffDays) and OtherPublicHoliday. PTI §9.3.5: "grouping elements shall not be used, and all bank holidays shall be explicitly stated" — so BODS files use the individual names.

#6 — VehicleJourneyTimingLink is never read ❌
This is the worst defect in the parser.

What the spec says
The override applies to timing links exactly as it does to profiles (§3.7, Figure 3-25):

A VehicleJourneyTimingLink may override any common property it shares with a JourneyPatternTimingLink.

§6.8.4.1 on RunTime: "Time taken to traverse link. Defaults to value specified for JourneyPatternTimingLink." Table 3-7 marks RunTime as R (required) at JourneyPattern level and O (optional, otherwise inherited) at VehicleJourney level. §3.7.2 says the same for wait times, resolved "through the VehicleJourneyTimingLink / JourneyPatternTimingLinkRef".

Critically, PTI blesses an encoding style that depends entirely on this. §8.1 describes the two ways files are built in practice:

There is a JourneyPattern, JourneyPatternSection and JourneyPatternTimingLink set for every different combination of link duration, wait time and stop activities…
There is a single JourneyPattern, JourneyPatternSection and JourneyPatternTimingLink set for each direction, with each link duration and wait time set to zero minutes. This method uses the facilities in the vehicle journey to override the default zero-minute durations for each of the links.
And §9.2: a VehicleJourney "may override the vehicle timings by providing a complete set of times over all of the links in a journey pattern in a set of VehicleJourneyTimingLink elements."

What your code does
ParserExtension.cs:182-220 builds stopsBySectionId exclusively from JourneyPatternTimingLink, and the vehicle journey loop at :277-307 looks up that precomputed list by section id. The string VehicleJourneyTimingLink does not appear anywhere in the file.

The failure
On a method-2 file, every RunTime is PT0M and every WaitTime is absent. So:

every entry in stopsBySectionId gets offset 0
every BusCallingPoint.ScheduledTime equals the journey's DepartureTime
ScheduledDayOffset is 0 everywhere
busCallingPoints.Count > 1, so the guard at :309 doesn't fire
The import succeeds. Nothing is logged. OriginDepartureKey is still built correctly from the first/last stop and departure time, so the row even joins to live SIRI data — it just claims the bus reaches all forty stops simultaneously. GetBusStopTimetable would then report that time at every stop on the route.

I checked all four sample XMLs in your repo and on the Desktop: zero occurrences of VehicleJourneyTimingLink. So this is entirely latent — it fires the first time a method-2 operator appears in the feed, and it fails silently when it does.

What a fix involves
Not a small patch, because it cuts against the current design. Today offsets are computed once per section and shared across all journeys using it. VehicleJourney-level timings are per journey, so they need a separate path:

Index JourneyPatternTimingLink by @id — your files do carry them (jptl_1, JPS_36_1), and integrity rule I9 mandates document-wide uniqueness, which is what makes JourneyPatternTimingLinkRef resolvable.
In the vehicle journey loop, if VehicleJourneyTimingLink children exist, build that journey's stop list from them instead of the cached section list.
Per link, resolve RunTime as VJTL → referenced JPTL, and WaitTime as VJTL From → JPTL From.
Take StopPointRef from the referenced JPTL, not the VJTL — PTI §9.4: "The From and To elements do not refer to the stop since this is inherited from the referenced journey pattern."
PTI §9.4 also guarantees "there must be a one-to-one mapping between the links in a set of VehicleJourneyTimingLink element and the underlying JourneyPattern", so you can assume complete coverage rather than patching partial overrides — on conformant files.

Rough size: an id index plus a second stop-list builder, call it 60–80 lines.


#11 — ServicedOrganisationDayType not modelled ❌
Spec
§6.11.1: "Specifies that the service runs or does not run on the working days or holidays of a nominated organisation such as a school or Local Education Authority. ServicedOrganisationDayType is ANDed with RegularDayType and any PeriodicDayType values."

The organisation itself is declared once at document level (§6.12) with an OrganisationCode, Name and WorkingDays date ranges, and journeys reference it by code.

PTI §9.3.6 explains the intended encoding, which is what makes this tractable:

serviced organisation dates restrict (are logically ANDed with) the days of the week provided in the RegularDayType element. So, for schools… this pattern can be stated as the regular days of operation. The dates provided for the serviced organisation then list the range of dates during which those Mondays to Fridays apply.

Two PTI simplifications worth banking:

"only WorkingDays shall be defined, and all other days that are not WorkingDays shall be assumed to be holidays" — Holidays must not be used. Term-time journeys are DaysOfOperation/WorkingDays; holiday-only journeys are DaysOfNonOperation/WorkingDays.
ParentServicedOrganisationRef is "Not used" in PTI — so Table 14-5's ancestor rules (rows 9/10, 19/20, 30/31) don't apply to BODS data at all. That removes the recursive part of the algorithm.
Your code
The document-level <ServicedOrganisations> collection is never read, and ServicedOrganisationDayType never resolved.

Impact
Over-reporting, and this is the most common real-world instance of the gap. A school bus coded RegularDayType Mon–Fri + ServicedOrganisationDayType/DaysOfOperation/WorkingDays (term ranges) imports as "runs every weekday, all year". Through August you'd advertise school services that don't exist.

None of your four samples use it, but it's widespread across the wider BODS feed — PTI §3.1 calls it "strongly recommended".


#15 — VehicleJourneyRef kills the document ❌ (recap)
ParserExtension.cs:241 throws when JourneyPatternRef is absent, but §6.8.1 gives a VehicleJourney two valid ways to find its pattern, and PTI §9.2 confirms it "shall have either a JourneyPatternRef … or a VehicleJourneyRef." Valid data, total file loss.

PTI makes the inheritance total: "all the details of the referenced VehicleJourney, including operating profile, timings, vehicle types, etc. shall be inherited and not overridden" — only DepartureTime and the real-time operational elements stay local. Fix is an index of journeys by VehicleJourneyCode, a hop to the target for pattern/profile/line/service, and a depth guard (rule X1 forbids self-reference but not A→B→C chains). Independent of #6 for method-1 files.



#16 — OperatorRef and NationalOperatorCode throws ❌
Two separate throws, both fatal to the whole document, both on elements that aren't actually mandatory.

VehicleJourney/OperatorRef — :237
Table 3-7 classifies each property as Required [R], optional-but-inherited [O], or always-inherited [I]. OperatorRef is R at Service, (R) at JourneyPattern, I at VehicleJourney, with the Default Value column giving Service / RegisteredOperator.

So a VehicleJourney omitting it should walk up to the JourneyPattern's OperatorRef, then to Service/RegisteredOperatorRef. Your samples happen to state it at all three levels, so you haven't hit it — the HIPK file carries tkt_oid on the VehicleJourney, the JourneyPattern and as RegisteredOperatorRef. A file that states it only where the schema requires it dies.

Operator/NationalOperatorCode — :115
This one has a datable cause. PTI v1.1 §2 says "NationalOperatorCode is mandatory" — and the tracked-changes markup on that line reads "Deleted: not required". It was optional in PTI v1.0 and was made mandatory in v1.1 (Aug 2020).

So any file predating v1.1, or any non-PTI TransXChange, may legitimately omit it — and your parser rejects the entire document over one absent element. Note the existing code already works hard to be forgiving about operator identity a few lines down, registering the id, the NOC and OperatorCode as lookup keys because "sometimes <id> in operator does not match with <OperatorRef>". The strictness at line 115 sits oddly against that tolerance.

Fix shape
Both are small. For OperatorRef, fall back through JourneyPattern → Service/RegisteredOperatorRef before throwing. For NationalOperatorCode, fall back to OperatorCode or the id and log — BusCallingPoint.OperatorRef at :333 just needs a stable operator identifier, not specifically a NOC.


#18 — DeadRun and short working ignored ❌
I under-sold this one originally. It's worse than "wrong origin stop".

Spec
§6.8.3.1: a DeadRun is "a positioning run at the start or end of a journey; it is used to place a vehicle in position to start the service, or to retrieve it at the end." ShortWorking marks where a dead run intercepts the pattern, and §3.7.1.2 defines the consequence: "Short Working: a vehicle journey that follows a journey pattern but omits one or more stops at one or other end of the journey."

PTI expects them — StartDeadRun and EndDeadRun are both "Where appropriate, shall be included".

The part I missed
PTI §9.7.2 redefines what DepartureTime even means when a dead run is present:

for the avoidance of doubt, TXC-PTI defines the DepartureTime of a VehicleJourney as either:
a) the departure time from the first stop on the VehicleJourney, where there is no StartDeadRun; or
b) the departure time of the StartDeadRun, where there is a StartDeadRun.

So with a StartDeadRun, DepartureTime is when the bus leaves the garage — not when it reaches its first passenger stop. Your code treats DepartureTime as the time at calling point one and adds offsets from there, so every stop time on such a journey is early by the whole dead-run duration. That's not a wrong endpoint; that's every published time wrong on that journey.

Three compounding failures
Extra stops. The full pattern is emitted, including stops before the interception point that the bus passes empty.
All times shifted. Per §9.7.2(b), by the dead-run length.
The live join breaks. OriginDepartureKey is departureTime + firstStopId + lastStopId. On a short working, all three components are wrong — wrong time, wrong first stop, wrong last stop. The SIRI feed reports the actual origin and destination, so the key never matches and the journey never joins to live data at all.
Fix shape
Bigger than #17, smaller than #6. Read StartDeadRun/EndDeadRun, use ShortWorking/JourneyPatternTimingLinkRef to find the interception link, trim the calling points outside it, and re-base the offsets so the first real calling point is at DepartureTime + dead-run RunTime. It needs the JourneyPatternTimingLink id index that #6 also needs — so if you do #6, do this alongside it.
